# EAI 代码结构与开发方式

## 目录职责

```text
eai_app/
  application/       启动、主窗口组合、独立执行进程客户端
  domain/            几何不变量、抓取状态机、手型、轨迹、任务定义和任务世界
  planning/          IK、碰撞场景、轨迹校验、可达空间、恢复规划
  perception/        RGB-D、点击位姿、多视角融合、分割与位姿模型协调
  adapters/          ROS、机器人、相机、模型服务、仿真后端的外部接口
  workers/           独立模型推理/评估进程，按业务分类
  tasks/
    phone_assembly/  手机盒装配程序、仿真和真机适配器
  ui/
    builders/        各页面的首次布局构造
    window/          主窗口的分功能控制方法
    grasp/           抓取面板、流程/执行/感知/配置控制器和显示逻辑
    robot/           三维视图、模型资产、渲染、叠加层和交互
    cameras/ chat/ simulation/ widgets/ ...
  configuration/     设置与默认值
  infrastructure/    存储、日志、旧 API 兼容层
  platform/          旧入口的环境及可选依赖引导
  development/       方法热更新、Qt 开发菜单和源代码一致性检查
  paths.py           PROJECT_ROOT 等稳定资源路径
tests/               单元测试和离线集成测试；data/ 存放固定测试数据
config/              用户标定、任务和场景配置（位置保持不变）
scripts/             运维/执行/回归入口
```

采用分层、适配器和界面控制器的组织方式。领域层不依赖 Qt 或 ROS；感知和规划使用共享领域几何校验。外部设备和服务接入放在适配器中。任务程序复用领域模型和执行适配器，不通过模拟按钮点击完成任务。

这是保持既有行为的渐进式重构。主窗口仍通过按功能划分的 mixin 组合，旧全局依赖通过限定到具体模块的 `ModuleRef` 连接，尚非完全依赖注入的独立页面系统。新增功能应优先使用显式构造参数/回调，不继续扩大兼容层或主窗口。

## 大文件如何定位

原约 60,000 行的 `show_camera_topics.py` 现在仅保留入口；主窗口组合位于 `application/main_window.py`。原来的 `build_heavy_ui` 拆成约 40 个页面构造器，跨构造器局部状态显式放入 `BuildContext`，布局顺序不变。

- 改手动控制布局：`ui/builders/manual_control.py`。
- 改机器人页布局：`ui/builders/robot_workspace.py`；三维显示在 `ui/robot/`。
- 改分阶段抓取：`ui/grasp/panel.py` 构造面板，其余控制器处理对应操作。
- 改多视角功能：`ui/window/multiview*.py`、`perception/multiview.py`。
- 改 IK/碰撞：`planning/`；任务状态和数据校验在 `domain/`。
- 查找原主窗口/ROS 节点方法：`application/viewer_registry.json` 的方法映射，或 `rg 'def 方法名' eai_app`。

根目录 Python 兼容入口和旧 `phone_assembly` 包转发到同一个实现模块，避免维护两份代码。已有 shell 启动命令、进程参数和导入路径继续可用；新代码请直接导入 `eai_app`。`source_path()` 使执行日志记录真实实现的哈希，而非入口文件哈希。

配置、模型、缓存、任务图片的路径统一以 `PROJECT_ROOT` 为基准，不能继续用某个新模块的 `__file__.parent` 猜项目根目录。不要把运行数据移动进源代码包。

## 不重启的修改范围

| 修改类型 | 当前行为 |
| --- | --- |
| 已加载的普通函数/方法体，签名和闭包布局不变 | 空闲时事务式更新；已连接的 Qt 回调保留身份并使用新代码 |
| 字符串、计算或显示逻辑位于普通方法内部 | 下次调用生效；不会重跑构造函数 |
| 尚未导入的模块/新启动 worker 的方法修改 | 语法检查通过后，在下一次导入/进程启动时读取 |
| 新增/删除模块或方法、导入、模块常量、签名、装饰器、类结构 | 提示需要重启 |
| 构造函数、页面 `build`/`build_*`、Qt 信号或布局结构 | 提示需要重启；不丢弃现有控件状态来强行重建 |
| ROS 生命周期、进程执行客户端/服务、平台引导、热更新器自身 | 提示需要重启 |
| 已在运行的模型服务器、原生依赖、URDF/非 Python 资源 | 不属于本监视器范围；按对应服务/资源加载方式重新加载 |

自动监视默认开启，每 1.5 秒扫描一次，两次稳定扫描后处理。菜单 **开发 → 热更新状态** 显示错误或需重启的原因；**Ctrl+Shift+R** 可手动检查。

更新前比较 AST，只允许函数体变化；不重新运行模块初始化、导入、装饰器或默认参数表达式。先校验整个变更批次，再修改原函数的代码对象，保留其全局环境、闭包、默认参数和对象状态。语法或兼容性错误不会部分应用。编辑中的半文件保存也会被延时/语法检查拦住。

抓取、规划、恢复、自动任务、暂停状态、持物或手动控制忙碌时延后应用，不会为更新代码自动停止或重启机器人。更新成功后清除旧抓取规划，要求重新规划。源文件尚未与界面一致时拒绝发起新的抓取规划/执行。执行客户端给新进程附上源代码版本，执行服务在构造运动后端前再次校验；独立字节码目录避免快速连续保存读取到旧缓存。该校验不是对运行中进程的动态代码替换。

## 回归验证

```bash
bash scripts/run_offline_tests.sh           # 两类环境都运行
bash scripts/run_offline_tests.sh ui        # 系统 Python / ROS / Qt
bash scripts/run_offline_tests.sh planning  # Pinocchio / Coal / MuJoCo 环境
```

可通过 `EAI_UI_PYTHON`、`EAI_PLANNER_PYTHON` 指定对应解释器。不要把 ROS 的系统 `hppfcl` 与规划环境的新版 Pinocchio/Coal 随意混装：二进制类型不兼容会使碰撞几何构造失败。

测试覆盖抓取门控、任务、感知、三维偏好、模型、原入口兼容、热更新和完整界面离屏构建。构建测试屏蔽线程启动、子进程、网络及相机访问；运动测试使用假节点、运动学或接触仿真。真机标定和硬件实测仍独立于这些回归。
